# AI Usage

This project was built with an AI coding assistant (Claude Code) as a pair programmer.

## How it was used

- I wrote the design (tables, flows, rules) and a step-by-step build plan before coding. The assistant worked one step at a time from that plan.
- For each step, the assistant proposed the work first. I approved it before any file changed.
- The assistant ran the checks (`php artisan test`, `pint --test`, `npm run test`, `npm run build`) before each step was marked done.
- I reviewed every diff and made every commit myself.
- When generated code differed from the plan, the assistant flagged it and I made the call.

## Step log

One line per finished step: what the assistant did, and what I checked or changed.

- **1.1 MySQL connection.** Switched `.env` / `.env.example` from SQLite to MySQL and set database drivers for cache, queue and session. Checked `migrate:status` and the tables in phpMyAdmin.
- **1.2 Sanctum + health API.** Installed Sanctum, enabled `statefulApi()`, added the `/api/v1` prefix and `GET /api/v1/health`. Opened the endpoint in the browser.
- **1.3 Response format + errors.** Added the `ApiResponse` envelope, a `BusinessException` base and central JSON exception rendering, plus feature tests. Reviewed that no internal details leak in 500 responses.
- **1.4 Vue 3 SPA shell.** Set up Vue, Router, Pinia, Vue Query and the axios client, the `app.blade.php` shell and the catch-all route. The assistant tightened the catch-all regex so pages like `/updates` are not excluded, and added a test for it.
- **1.5 Clone-and-run.** Updated the `composer setup` script, moved PHPUnit to a MySQL `oms_testing` database (with `force="true"` so tests can never hit `oms`), and added Vitest with a sample test, a Pint config, this file and the README Quick Start. Verified `composer setup` against a fresh database.
- **2.1 Users + roles/permissions.** Added `is_active`, `last_login_at` and soft deletes to users, installed spatie/laravel-permission, and seeded 20 permissions, 3 roles and 6 demo users. The test spells out the permission matrix by hand instead of reusing the seeder constants, so a wrong seeder cannot pass its own test. I asked to keep it simple, so demo users live in `DatabaseSeeder` instead of a separate seeder.
- **2.2 Customers.** Added the `CustomerStatus` enum, the customers migration with named indexes (unique email, status + created_at, FULLTEXT on name/email/company), the model, factory and model tests. Checked the indexes with `SHOW INDEX` and that the migration rolls back cleanly.
- **2.3 Products.** Added the `ProductStatus` enum, the products migration (price in cents, tax in basis points, unsigned stock, named indexes), the model with `stock_quantity` kept out of `$fillable`, a factory with inactive/discontinued/low-stock states, and model tests, including one that proves the database refuses negative stock.
- **2.4 Orders + order items.** Added the `OrderStatus`, `OrderPriority` and `DiscountType` enums, the orders and order_items migrations with the planned indexes, the models and relations, and factories. Totals, status, version and the order number are kept out of `$fillable`. Tests cover the order-number format, snapshots, cascade on items and restrict on customers. I checked in information_schema that MySQL reused the composite indexes for the foreign keys, with no duplicate FK indexes.
- **2.5 History, notes, activities.** Added the order_status_histories, order_notes and order_activities tables, each indexed on `(order_id, created_at)` and cascading with the order. History and activities are append-only (no `updated_at`). Added an `OrderActivityType` enum for the fixed activity types, plus three models, Order relations, a note factory and tests.
- **2.6 Audit, stock ledger, notifications.** Added the audit_logs table (3 indexes, append-only), the stock_movements ledger (signed quantity, balance_after), the `StockMovementType` enum, and the notifications table. Replaced its default morph index with `(notifiable_type, notifiable_id, read_at)` for the unread-count poll. Added the models, `Product::stockMovements()` and tests. I chose not to add an audit event enum, because the Auditable trait in a later step defines those values.
- **2.7 Demo seeder.** Built `DemoDataSeeder`: 100 customers, 50 products and 600 orders over 6 months, bulk-inserted in one transaction (about 1 s). Each order follows a valid status path with matching history, activities and audit rows. Totals use the planned pricing formula. Stock has an opening-balance ledger entry, so product stock always equals the sum of its ledger. A consistency test checks totals, history, stock and assignment, and passed across repeated random runs. Fixed along the way: a factory-closure `$this` bug, inconsistent actors between history and ledger, a status mix that was too skewed to completed, and lorem-ipsum product names.
- **3.1 Login / logout / me API.** Added `AuthService` (attempt with `is_active`, session regenerate, `last_login_at`; logout invalidates the session and the CSRF token), `LoginRequest`, `UserResource` (roles + permissions for the SPA) and a thin `AuthController`. Verified the real flow with curl against the dev server (csrf-cookie → login → me → logout → 401, and 419 without a CSRF token). That check showed a login without a stateful Referer returned 500 ("Session store not set"), so it now returns a clear 400, with a test. Pint also flagged an old formatting issue in `bootstrap/app.php`, fixed with no logic change.
- **3.2 Inactive-user middleware + login throttling.** Added the `EnsureUserIsActive` middleware (alias `active`, on the `auth:sanctum` group), which logs out a user deactivated mid-session and returns 401. Added a `login` rate limiter (5/min per email + IP). Verified on the dev server: the 6th attempt returns 429 with Retry-After, and deactivating a logged-in user gives 401 on their next request. The user was re-activated right after the check.
- **3.3 Vue login page, auth store, route guards, logout.** Added `api/auth.js`, the Pinia `auth` store (`can()`, `fetchUser` once per page load), router guards (`requiresAuth`, `guestOnly`, `permission` → Forbidden), a global 401 handler registered from `main.js` (avoids a circular import), the Login page (422 under the field, 429 wait time, open-redirect-safe `redirect`) and a header with Logout that clears the Vue Query cache. Added Vitest specs for the store, guards and login page (13 tests). Checked in Chrome: redirect to login, wrong password, login, refresh keeps the session, `/login` redirects home, logout. The check also found a margin-collapse white strip on the login page, fixed with padding.
- **4.1 Customers CRUD API.** Built the module pattern: route `->can()` + `CustomerPolicy` (permissions, not roles), Form Requests (list whitelist, store/update, status), `CustomerService` (sets `created_by`; refuses to delete a customer with orders), `CustomerFilter` (FULLTEXT boolean prefix search with operators stripped, prefix LIKE for words under 3 characters, sort whitelist + id tie-break), `CustomerResource`, and `ApiResponse::paginated()`. Search tests use `DatabaseTruncation` because InnoDB FULLTEXT only sees committed rows, and they truncate afterwards so other tests start clean (suite passes in normal and reverse order). The dev-server check found unauthorized users got 422 before 403. I chose route-level `->can()` so permission is checked before validation. EXPLAIN confirms search uses `idx_customers_search`.
- **4.2 Products CRUD API.** Built it on the customers pattern: route `->can()` + `ProductPolicy` (`products.view` for all, `products.manage` for admin only), Form Requests (SKU uppercased and validated by regex and uniqueness; price as integer cents; tax in basis points; `stock_quantity` never accepted), and `ProductService`. On create, an optional `initial_stock` writes an "Opening stock" ledger row in the same transaction, so stock always equals the ledger sum. Also added `ProductFilter`, `ProductResource` (cents + `price_formatted`, `is_low_stock`) and `App\Support\Money` (integer-only formatting). The FULLTEXT/prefix search moved into a shared `SearchesText` trait that both filters use. There is no DELETE route, per the plan; products are discontinued instead.
- **5.1 OrderPricingCalculator.** Pure class with no DB or facades and integer cents only, implementing PLAN §4. It prorates the discount with leftover cents to the largest line, applies tax per line after discount, and rounds half up via integer maths. Extra line keys pass through so callers keep their snapshots. Unit tests cover the exact assessment example (36300, line discounts 1143/857, tax 1886/1414), rounding, the discount cap, leftover cents, mixed tax rates, invalid input, and 500 seeded random orders checking that line amounts always sum to the totals. `DemoDataSeeder` now uses the calculator instead of its own copy of the formula; reseeded with 0 total mismatches.
- **5.2 Create order.** Added `StoreOrderRequest` (the assessment validation messages verbatim; active customer and products; distinct products; percent ≤ 100%; assignee must be an active manager or staff member; status only draft or pending; client totals and prices are not in the rules, so they are dropped). `OrderService::create` runs one `DB::transaction`: products loaded in one query and re-checked, `OrderPricingCalculator`, order insert, `order_number` from the id, bulk item snapshots, first status-history row, activity (and an optional first note). Stock is not touched until confirmation. Added `OrderPolicy@create` with a route `->can()`, plus `OrderResource`/`OrderItemResource`/`UserSummaryResource`. Tests include the assessment example via the API (36300, tampered totals ignored) and a forced failure after the order insert that proves the whole transaction rolls back. Fixed a null-assignee resource crash before it shipped. The dev-server check created ORD-10601 with backend-computed totals.
- **5.3 Order listing.** Added `GET /orders` with `Order::visibleTo()` (staff see only assigned orders, at the query level, and filters cannot widen it). `OrderFilter` chooses an index-friendly path per search type: order number → primary key; customer → FULLTEXT `whereIn`; product → FULLTEXT + `EXISTS` on order_items; assignee → prefix LIKE. Also filters (status[], priority[], customer, assignee, date range), a sort whitelist (customer via correlated subquery, status in workflow order via FIELD), selected columns and eager loads with column lists. Turned on `Model::preventLazyLoading()` outside production (only one test needed an eager load). Tests include staff scoping and a query-count test. That test first failed because of Spatie permission cache warm-up, not an N+1, and was fixed with a warm-up request. Also fixed the shared search so short terms like "CH-77" keep their dash. Verified on the dev server (staff1 sees exactly their 178 orders) and with EXPLAIN.
- **5.4 Show / update / delete.** Added `OrderPolicy@view` (staff only their assigned order), plus update and delete. `GET /orders/{id}` returns the full customer contact and address for the detail page. Update uses optimistic locking: `lockForUpdate`, then the client-sent `version` must match or a 409 `ConcurrencyConflictException` is thrown; `version + 1` on save. Draft/pending orders reprice through the shared calculator path and rewrite items; confirmed and later allow only priority (other fields are `prohibited`); completed/cancelled orders are not editable. Status and assignee are refused on PUT so their own endpoints stay the single path. Delete is admin-only, soft, and only for draft/pending/cancelled. Added `OrderStatus::isEditable/isTerminal/isDeletable` and refactored `OrderService` to share pricing, item insert and activity helpers. Fixed the tests to `fresh()` factory orders (version default) and set `version => 1` in `OrderFactory`. Verified on the dev server: staff 200/403, edit → version 2, stale edit → 409, manager delete → 403.
- **5.5 Status workflow.** Added the state machine to `OrderStatus` (`allowedTransitions`, `canTransitionTo`). `OrderPolicy::changeStatusOf` (route level) and `changeStatus($order, $to)` decide who may make each move, by permissions: fulfilment moves for `orders.change_status` (staff on their own orders), commercial moves for `orders.update`, cancel for `orders.cancel`, and ready → cancelled also needs `orders.delete`, which makes it admin-only. `OrderStatusService::transition` locks the row, checks the state machine (`InvalidStatusTransitionException`, the assessment message), sets lifecycle timestamps and the cancellation reason, bumps `version`, and writes history and activity. A reason is required to cancel. Added `allowed-transitions` (per-user buttons) and `status-history` (oldest-first timeline). `DETAIL_RELATIONS` moved to `OrderResource` for reuse. Tests cover all 49 transition pairs, role rules and a double-confirm race. In the dev-server check I deliberately did not confirm a real order, because stock deduction arrives in 5.6.
- **5.6 Stock deduct / restock.** Added `InventoryService` as the only place stock changes. Each deduction is one atomic conditional UPDATE (`stock_quantity >= qty`); zero affected rows throws `InsufficientStockException` and the caller's transaction rolls back everything. Products are processed in id order to keep a consistent lock order and avoid deadlocks. Every change writes a ledger row with `balance_after`. `OrderStatusService` deducts on confirm (sets `stock_deducted_at`) and restocks on cancel only when stock was deducted, with matching activity entries. Added `POST /products/{id}/stock-adjustments` (admin, signed quantity, reason required, cannot go negative). Tests cover the assessment 100 → 95 example, rollback of an already-deducted product when a later one is short, no double-selling of the last units, restock on cancel and none for pending, no repeat deduction on later steps, and stock equal to the ledger sum. Verified on the dev server, including the rollback, and cancelled the test order ORD-10602 afterwards.
- **5.7 Assign, notes, activity feed, audit trait.** Added the `Auditable` trait (Order, Customer, Product). It hooks created/updated/deleted/restored and stores only changed fields as raw old/new values, excluding timestamps, version and hidden fields, with user, IP and user agent. It runs inside the caller's transaction, so rolled-back changes leave no audit row. Order names its update events `status_changed` / `assignment_changed`. The order-number write uses `saveQuietly()` to avoid a noise audit, and `DemoDataSeeder` runs `WithoutModelEvents` because it writes its own audit rows. Added `POST /orders/{id}/assign` (`orders.assign`, reusable `AssignableUser` rule, null unassigns, terminal orders refused, version bump, activity), notes list/add (`notes.create`; staff only on their own orders), and an `activities` feed (paginated, newest first). Tests cover the audit event sequence of a full order lifecycle, changed-fields-only diffs, rollback without audit, assignment rules and staff note scope. Verified on the dev server.
- **6.1 Layout + UI kit.** Added `AppLayout`/`AppSidebar`/`AppHeader`. The sidebar comes from `config/navigation.js` and shows a link only if its route exists and the user has a permission for it, so pages appear as they are built. The header has the role badge, logout and a mobile menu toggle. Reusable components follow the assessment list: BaseButton (variants, loading), BaseInput/BaseSelect/BaseDatePicker (v-model, label, error, aria), BaseBadge, BaseCard, BaseModal (Teleport, Escape/backdrop close), ConfirmDialog, DataTable (cell slots, skeleton rows, empty state, row-click), Pagination (API meta), SkeletonLoader, EmptyState, ErrorState (retry), a Pinia toast store with ToastContainer (aria-live), and a `v-can` directive. Pages opt out of the layout with `meta.layout: false`; the header title comes from `meta.title`. Home uses the new loading/error states. Vitest 29 tests. Checked in Chrome: desktop layout, Forbidden page in the layout, and the mobile layout at 390px in an iframe (no horizontal scroll, menu button shown, name hidden). The menu slide-in looked stuck, but the automation tab was hidden, which pauses CSS transitions; with the transition disabled the sidebar opened correctly.
