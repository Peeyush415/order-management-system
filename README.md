# Order Management System

A production-style Order Management System for an internal sales/operations team: a Laravel REST API (`/api/v1`) and a Vue 3 single-page app served from the same Laravel application.

Staff create customers and products, build orders (multiple products, quantities, discount, tax), assign them to employees, move them through a status workflow that reserves stock, add notes, and follow every change in an activity feed and an audit log. Managers watch performance on a dashboard; admins manage users, roles and permissions.

## Features

- **Orders:** five-step create/edit wizard with a live price preview; totals always recalculated on the server (integer cents, prorated discount, tax per line); search, filters, sorting and pagination kept in the URL.
- **Status workflow:** `draft ⇄ pending → confirmed → processing → ready → completed`, any open state → `cancelled`. Confirming deducts stock atomically; cancelling a confirmed order restocks. Every change has a history row (from, to, user, time, remarks).
- **Concurrency:** optimistic locking (`version`, 409 on a stale edit), row locks for status and assignment changes, and a conditional stock update that can never oversell.
- **Assignment, notes, activity feed** per order; **notifications** (assigned, confirmed/cancelled/completed, low stock) through queued listeners, shown in a header bell.
- **Dashboard:** ten figures for a date range, status distribution and a day/week/month revenue trend, cached with versioned keys. Staff get a "My work" view instead.
- **Customers and products** with stats, stock adjustments and a stock ledger.
- **Users, roles and permissions:** permission-based access (not role names), a role/permission matrix, and safeguards so the last admin can never be locked out.
- **Audit log** of every important write with readable old → new values ("Priority: Normal → High").

## Quick Start

```bash
git clone <repo-url> order-management-system && cd order-management-system
cp .env.example .env            # set DB_USERNAME / DB_PASSWORD; create an empty database "oms"
composer setup                  # install, key, migrate + seed, build frontend
composer run dev                # http://localhost:8000  (server + queue worker + vite)
```

Create the database first, for example:

```sql
CREATE DATABASE oms CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

> `composer setup` runs `migrate:fresh --seed`, so running it again **resets all data** in `oms`.

Without the composer scripts:

```bash
composer install
php artisan key:generate
php artisan migrate --seed
npm install && npm run build
php artisan serve               # terminal 1
php artisan queue:work          # terminal 2 (notifications are queued)
```

## Environment variables

All variables live in `.env.example` with safe local defaults and no secrets. `APP_KEY` is generated by `composer setup` (`php artisan key:generate`). The ones this project relies on:

| Variable | Default | Purpose |
|----------|---------|---------|
| `APP_URL` | `http://localhost:8000` | Base URL of the app |

| `CACHE_STORE` / `QUEUE_CONNECTION` | `database` | No Redis needed to run locally |

## Database

Migrations create these tables (plus Laravel's `sessions`, `cache`, `jobs`, `failed_jobs` and spatie's role/permission tables):

| Table | Holds |
|---|---|
| `users` | Accounts with `is_active` and `last_login_at`; one role each |
| `customers`, `products` | Master data; products keep `stock_quantity` (never below zero), price in cents, tax in basis points |
| `orders`, `order_items` | Orders with server-calculated totals and a `version` for optimistic locking; items snapshot product name, SKU, price and tax |
| `order_status_histories`, `order_notes`, `order_activities` | Per-order timeline, notes and human-readable activity feed (append-only) |
| `stock_movements` | Stock ledger: every change with its reason and the balance after it |
| `audit_logs` | Who changed what, with old/new values, IP and user agent (append-only) |
| `notifications` | Database notifications for the bell |

The main list, filter and dashboard queries have named indexes chosen for them (for example `idx_orders_assigned_status_date` for a staff user's orders and the covering `idx_orders_date_status_total` for the dashboard), checked with `EXPLAIN`. `customers` and `products` have FULLTEXT indexes for search.

**Seeders** (`php artisan migrate:fresh --seed`, about 3 seconds): 3 roles with 20 permissions, 6 demo users, 100 customers (10 inactive), 50 products (some low on stock), and 600 orders over the last 6 months with a realistic status mix. Each order has 1–5 items, a status history that follows the workflow, notes, activities, audit rows and stock-ledger entries consistent with its path.

## Architecture

```
Vue SPA ──(cookie session + CSRF)──▶ routes/api.php  ->can() permission check (403 before validation)
                                          │
                                   FormRequest (validation)
                                          │
                                   Controller (thin: authorize, call service, return Resource)
                                          │
                                   Service (business rules, DB::transaction, row locks)
                                    │            │              │
                              Models + Auditable  Events ──▶ queued listeners (after commit) ──▶ notifications
                                          │
                                   API Resource ──▶ { success, message, data, meta }
```

- **One Laravel app, one origin.** The SPA is served by a catch-all Blade view, so Sanctum cookie sessions work without CORS or tokens in the browser.
- **Permissions, not roles.** Code checks permissions (`orders.cancel`), never role names; roles are editable bundles. Every route has `->can()`, controllers call `Gate::authorize()`, and list queries are scoped too (`Order::visibleTo($user)`), so staff can't reach other orders through a filter or a guessed id.
- **Business logic lives in services** (`OrderService`, `OrderStatusService`, `InventoryService`, `OrderPricingCalculator`, …). Controllers stay thin and never trust totals from the client.
- **Money** is integer cents and tax rates are basis points; the pricing calculator uses integer maths only (the assessment example gives exactly 36300). A BigInt mirror on the frontend shows the same preview.
- **Order lifecycle:** an `OrderStatus` enum is the state machine; `OrderPolicy` decides who may make each transition. A status change locks the order row, checks the transition, updates stock, and writes history, activity and audit rows in one transaction.
- **Stock:** `UPDATE … SET stock = stock - ? WHERE id = ? AND stock >= ?`. Zero affected rows means insufficient stock, and the whole confirmation rolls back. Products are locked in id order, so two orders can't deadlock.
- **Audit:** an `Auditable` model trait writes changed fields only, inside the same transaction, so an audit row can never outlive a rolled-back change. Sensitive fields never reach it.
- **Events and queue:** services dispatch `OrderCreated`, `OrderAssigned`, `OrderStatusChanged`, `ProductStockLow`. Listeners implement `ShouldQueueAfterCommit`: they run in the background and only after the transaction commits.
- **Caching:** dashboard results are cached for 5 minutes under versioned keys; any order, customer or product write bumps the version after commit. This works on any cache driver (no tags needed).
- **Frontend:** Vue Query owns server state (caching, retries, invalidation after writes); Pinia only holds the logged-in user and toasts. Route guards and a `v-can` directive hide what a user can't do, while the API still enforces it.

More detail, including performance, security and scaling notes: [`docs/TECHNICAL_NOTES.md`](docs/TECHNICAL_NOTES.md).

## Trade-offs

| Decision | Alternative considered | Why |
|---|---|---|
| Sanctum SPA cookie sessions | API tokens in local storage | HttpOnly cookies can't be read by injected scripts; CSRF is handled by Laravel. Tokens only pay off for third-party or mobile clients. |
| Integer cents + basis points | `DECIMAL` columns or floats | Exact arithmetic in PHP and JS, no rounding drift, one rounding rule in one place. |
| Optimistic locking for order edits | Pessimistic locks while a user edits | Edits take minutes in a form; holding locks that long is impossible. A 409 with "reload" is honest and cheap. |
| MySQL FULLTEXT search | Laravel Scout + Meilisearch/Algolia | No extra service to run; prefix boolean mode covers names, emails and SKUs. Scout is the next step at a larger scale. |
| Database queue and cache | Redis | Runs anywhere with zero setup; switching is `QUEUE_CONNECTION=redis` / `CACHE_STORE=redis`. |
| Polling the unread count every 30 s | WebSockets (Reverb + Echo) | Far less moving parts; a 30-second delay is fine for these notifications. The events already exist, so broadcasting can be added later. |
| Small custom chart components | Chart.js / ECharts | Two simple charts; saves ~200 KB, stays accessible, and is easy to test. |
| No Docker | docker-compose | The brief allows XAMPP-style setups; fewer requirements for reviewers. |
| Soft delete only where history allows | Hard deletes | Customers with orders, users and products are deactivated instead, so orders and audit rows keep their references. |

## Tests and code style

Backend tests use a **separate MySQL database `oms_testing`** (set in `phpunit.xml`), because FULLTEXT search and date functions are MySQL-specific. Host and credentials come from `.env`.

```bash
mysql -u root -e "CREATE DATABASE oms_testing CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"

php artisan test                # backend tests (database: oms_testing)
npm run test                    # frontend tests (Vitest)
./vendor/bin/pint --test        # code style check (composer lint to fix)
npm run build                   # production assets
php artisan migrate:fresh --seed  # reset demo data
```

Covered: authentication, order creation (the assessment total, client totals ignored), validation, update with version conflicts, every valid and invalid status transition, stock deduction and rollback, authorization for each role (including list scoping), customers, products, users/roles lockout rules, audit rows, notifications, dashboard figures and query counts. Frontend tests cover money and pricing utilities, the router guard, the order wizard, forms with server errors, list filters, dashboard, badges and the admin screens.

## Project layout

```
app/
  Enums/                 OrderStatus (state machine), priorities, discount types, …
  Events/ Listeners/ Notifications/   order and stock events, queued notifications
  Filters/               list filters (search, whitelisted sorting)
  Http/Controllers/Api/V1/   thin controllers
  Http/Requests/         validation per endpoint
  Http/Resources/        response shapes
  Models/ (Concerns/)    Eloquent models, Auditable trait
  Policies/              permission + ownership checks
  Services/              business logic (orders, status, inventory, pricing, dashboard, users, roles)
  Support/               ApiResponse, Money, CacheVersion, audit value formatting
database/                migrations, factories, seeders
routes/api.php           REST API under /api/v1
routes/web.php           SPA catch-all: every non-API path returns the Vue shell
resources/js/            Vue 3 SPA (api/, composables/, components/, pages/, router/, stores/)
tests/                   PHPUnit feature and unit tests
docs/                    API.md, Postman collection, TECHNICAL_NOTES.md, AI_USAGE.md
```
